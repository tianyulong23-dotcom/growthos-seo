# ADR-CP-0001: Related Keywords 30 种子调用合同

## 状态

已接受。

## 日期

2026-08-05

## 背景

`docs/内容计划流程设计-V1.0.md` 的 CP-00 与 CP-03 要求向 DataForSEO Related Keywords Live 端点发出一个 HTTP 请求，并在该请求中提交 30 个带唯一关联标识的种子请求项。需求还明确规定：若供应商不支持，不得私自拆成 30 次调用、改变批量大小或增加其他来源，必须提交 ADR 后停止。

## 证据

DataForSEO 官方文档：

<https://docs.dataforseo.com/v3/dataforseo_labs-google-related_keywords-live/>

官方合同明确写明：

- `each Live API call can contain only one task`；
- 请求 task 使用单数 `keyword` 字段；
- 最多 30 指“可同时发送的调用数”，不是一个 HTTP 请求内可包含的 task 数；
- `tag` 只用于标识单个 task，并在该 task 的响应 `data` 中回显。

当前唯一凭据还曾返回 HTTP `401` / DataForSEO `40100`。该响应发生在任务受理前，不能作为 30 项支持性证据；但官方文档已经足以确认公开 Live 合同不支持单次 30 task。

## 决策

采用方案 A。内容计划仍以 30 个种子作为一个服务端逻辑批次，但按照供应商公开合同，为每个种子发出一个只包含单个 task 的 Related Keywords Live HTTP 请求。调用由 worker 服务端受控并发，前端只创建和查询整个内容计划批次，不逐词调用供应商。

每个逻辑请求独立保存稳定 `request_key`、`request_index`、种子 ID、唯一 `tag`、供应商请求 ID、状态、结果数和实际费用。部分失败只影响对应种子，已经成功或明确空结果的组必须保留。响应 `tag` 与请求不一致时，不能依赖数组位置猜测归属，记为 `uncertain`。

原费用公式 `$0.012 + 种子数 × $0.00012` 不再作为合同或预算事实。批次费用是 30 个单 task 响应中实际 `cost` 的总和；预估费用必须在有效凭据真实验证后另行固化。

## 可选方案

### 方案 A：30 次单 task Live 调用（已采用）

为 30 个种子分别调用 Related Keywords Live，可受控并发最多 30。每次调用保留独立 `tag`、任务 ID、费用和失败状态。

影响：符合供应商公开合同，但改变了原“一次 HTTP 请求”的固定要求；费用改为逐 task 审计并汇总，待有效凭据补充真实费用基线。

### 方案 B：改用支持多关键词输入的其他 DataForSEO 端点

例如重新评估已有 Keyword Ideas 等多关键词端点是否满足“相关词”业务语义，再用真实请求验证字段、分组、质量和费用。

影响：可以保留单次批量请求，但数据来源、相关性语义、结果分组和费用都会变化，不能仍称为 Related Keywords。

### 方案 C：与供应商确认非公开批量合同

要求 DataForSEO 提供可在一个 HTTP 请求中提交 30 个 Related Keywords task 的正式接口、账户能力或书面合同，再以有效凭据执行 CP-00。

影响：可以保留当前业务要求，但在供应商确认前无法估算可行性和时间。

### 方案 D：保持阻塞

不改变当前业务合同，也不实现内容计划后续流程。

影响：完全遵守现有需求，但 D1 及后续 D2-D7 均无法继续。

## 后果

- 流程 0 接入核查保留。
- D1 以“30 个服务端单 task Live 调用”的优化合同继续验收，通过后允许进入 D2。
- CP-00 不再要求证明一个 HTTP 请求可携带 30 个 task；它改为验证单 task 序列化、30 个逻辑请求、tag 映射、空结果、部分错误、费用、请求 ID 和并发上限。
- CP-03 和 CP-05 后续编排必须逐种子使用内容计划外部请求账本，不能让 Temporal 自动重试可能计费的调用。
- 本 ADR 不授权实施 D3-D7，也不改变两份 V1.0 参考文档中的其他业务规则。
