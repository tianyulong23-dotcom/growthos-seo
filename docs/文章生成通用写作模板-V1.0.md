# 文章生成通用写作模板 V1.0

## 1. 模板定位

本文件是文章生成流程的写作参考，不是验收合同、固定大纲、示例文章或竞品分析报告。

它可以为四个阶段提供参考：

1. 生成文章计划。
2. 按章节写作。
3. 合并并统一全文。
4. 检查文章是否仍有明显问题。

核心原则：**文章结构由用户问题和文章类型决定，不由固定字数或统一大纲决定。**

使用方式：

- 本模板提供常见的高质量写法，不要求每篇文章逐条符合。
- 可以合并、删除、增加或调整任何建议模块，只要更适合当前主题、证据和读者任务。
- 不因为字数、段落长度、H2 数量、模块顺序、没有 FAQ、没有结论、没有表格或没有 CTA 而判定文章不合格。
- 当模板建议与自然表达、完整答案或用户明确要求冲突时，以用户任务和文章质量为准。
- 只有真实性、证据边界、必要安全警告、用户锁定要求和不得抄袭等底线属于硬约束。

一篇好文章通常帮助目标读者完成一个明确任务，例如：

- 理解一个问题。
- 学会完成一件事。
- 比较多个选项。
- 选择适合自己的产品或方案。
- 判断某件事是否值得。
- 找到合适的本地服务商。

## 2. 可用输入

### 2.1 核心输入

| 字段 | 说明 |
| --- | --- |
| `primary_keyword` | 文章重点处理的主题或主问题，不等于必须重复出现的词组 |
| `language` | 正文语言 |
| `country_or_market` | 决定价格、政策、产品和用语适用范围 |

核心输入不完整时，可以从项目资料和研究结果中合理推导；无法可靠推导的内容不应凭空假定。

### 2.2 补充输入

| 字段 | 使用规则 |
| --- | --- |
| `secondary_keywords` | 只映射到自然相关的子问题，不为覆盖关键词增加无关章节 |
| `target_audience` | 谁在阅读，以及其知识水平和决策阶段；未知时可以根据主题采用合理的普通读者假设 |
| `required_questions` | 研究中发现的重点问题，用于检查覆盖面，不要求每个问题单独建立章节 |
| `research_evidence` | 可以支持事实、数据和判断的资料；需要具体外部事实时尤其重要 |
| `search_intent_signal` | 已知的搜索意图信号；未明确提供时，由计划阶段结合关键词、读者问题和搜索结果识别 |
| `article_type` | 用户锁定时必须遵守；未锁定时由搜索意图选择 |
| `title` | 锁定时原样保留；未锁定时根据主问题生成 |
| `writing_direction` | 锁定要求必须逐条落实，不得静默忽略 |
| `internal_links` | 只放入与当前段落直接相关的位置 |
| `official_project_facts` | 只有项目产品确实能回答当前问题时才使用 |
| `cta_targets` | 只有存在自然下一步时才使用，不能为了转化破坏中立答案 |
| `competitor_gaps` | 用于补足问题和证据，不复制竞争文章的表达或大纲 |

### 2.3 与当前研究包的字段映射

本节使用的是写作语义字段。接入现有生成链时按下表映射，不要求运行时重复创建同义字段。

| 写作语义字段 | 当前运行时来源 |
| --- | --- |
| `primary_keyword` | `keyword` |
| `language` | `language` |
| `country_or_market` | `country` |
| `target_audience` | `project.profile` 中与受众、业务和决策场景相关的资料；当前没有固定的同名顶层字段 |
| `search_intent_signal` | 当前没有固定的同名顶层字段；计划阶段根据 `keyword`、`reader_questions`、`serp_results` 和 `serp_observations` 推导，并写入 `ArticlePlan.search_intent` |
| `required_questions` | `reader_questions`，其上游来源为研究包中的 `required_questions` |
| `research_evidence` | `research_sources`，计划生成后再通过 `claims`、`claim_ids` 和来源映射约束章节 |
| `competitor_gaps` | `competitor_research.coverage_opportunities` 及相关竞品研究字段 |
| `secondary_keywords` | `secondary_keywords` |
| `article_type` | `requested_article_type` |
| `title` | `planned_title` |
| `writing_direction` | `writing_direction` |
| `internal_links` | `internal_sources`，计划生成后映射到 section 的 `internal_urls` |
| `official_project_facts` / `cta_targets` | `project.profile` 中经过核验的业务资料和 CTA 字段 |

如果某个语义字段无法从运行时输入可靠映射，则按输入缺失处理，不能假定模型已经知道该信息。

### 2.4 输入不足时的处理

- 没有证据时，不编造数字、日期、政策、测试结果、价格或用户评价。
- 无法确认的内容应缩小表述范围、明确不确定性，或从文章中删除。
- 没有真实产品数据时，不生成虚假排行榜。
- 没有本地服务商数据时，不生成伪造的本地目录。
- 主问题本身不清楚时，优先缩小主题或采用合理解释，不用宽泛背景知识掩盖问题。

## 3. 先选择文章类型

通常先选择一个最接近的主要类型，再按需要借用其他类型的局部结构。混合结构本身不是问题，关键是阅读逻辑是否自然。

| 文章类型 | 用户核心任务 | 主要输出 |
| --- | --- | --- |
| `Guide` | 理解主题并作出判断 | 直接答案、关键因素、条件、结论 |
| `How-To` | 完成一个具体任务 | 前置条件、步骤、验证、故障处理 |
| `Comparison` | 在两个或多个选项中选择 | 结论、统一维度比较、场景建议 |
| `Listicle` / `Best X` | 从候选项中选出合适选项 | Top picks、逐项评估、方法、选购标准 |
| `Review` | 判断单个产品或服务是否值得 | 结论、适合人群、实测/证据、优缺点、替代项 |
| `Directory` / `Local` | 找到并筛选服务商 | 可核验实体数据、地区入口、筛选标准、下一步 |

选择规则：

- “what / why / pros and cons / is it worth it”通常选择 `Guide`。
- “how to / steps / fix”通常选择 `How-To`。
- “A vs B / compare / difference”通常选择 `Comparison`。
- “best / top / options”通常选择 `Listicle`。
- “[product] review”通常选择 `Review`。
- “near me / in [location] / companies”只有在有真实实体数据时选择 `Directory`。

搜索结果的常见页面类型可以影响选择，但不能覆盖用户锁定的类型，也不能要求文章复制某个竞争页面。

## 4. 所有文章共用的骨架

### 4.1 H1

- 通常只使用一个 H1。
- H1 直接表达主问题、具体承诺或比较对象。
- 年份只有在内容确实具有时效性并会持续维护时才使用。
- 不使用“Ultimate”“Everything You Need to Know”等无法兑现的空泛承诺。
- 在结构化生成中，H1 由 `ArticlePlan.title` 表示，不作为 `sections[]` 中的独立章节，也不由章节写作阶段重复输出。

### 4.2 导语和直接答案

建议英文长度：`100-180` 词。

通常可以完成：

1. 在前 1-3 句直接回答主问题。
2. 说明答案成立的主要条件或例外。
3. 告诉读者正文将帮助其完成什么决定或行动。

不要从行业历史、宏观趋势或主关键词定义开始，除非它们是理解答案的必要前提。

主问题应有一个清楚的主要回答位置。简单问题可以直接由导语完整回答；复杂问题可以先在导语给摘要，再在正文展开。这里不要求额外创建一个固定的 owner section。

### 4.3 快速答案模块

根据意图选择一个主要模块，不要全部堆叠：

- `Key takeaways`：3-5 条真正的结论。
- `At a glance`：优缺点或关键因素列表。
- `Comparison table`：多个选项使用统一字段横向比较。
- `Top picks`：先展示类别、选择和关键差异。
- `Requirements`：操作文章先列准备条件。

建议英文长度：`60-150` 词，不含高密度表格中的数据。

### 4.4 正文

- 通常使用 3-8 个主要 H2。
- 每个 H2 通常围绕一个主要问题，但紧密相关的问题可以合并处理。
- H3 用于拆分步骤、比较维度、产品、优点、缺点或子问题。
- 在结构化生成中，每个正文 H2 对应一个 `ArticlePlan.sections[]` 项；导语、FAQ 和结论也可以是独立的顶层 section。H3 是某个 section 的 Markdown 内部结构，不单独占用一个 section。
- 标题应让只扫描标题的读者也能理解文章逻辑。
- 不使用无信息量的 `Introduction`、`Main Body`、`More Information` 标题。

每个正文小节优先采用：

1. **答案或判断**：首句说明这一节的核心结论。
2. **证据或解释**：提供事实、数据、步骤、规格或因果关系。
3. **用户意义**：解释这对读者的成本、风险、结果或选择意味着什么。
4. **限制或条件**：在确有必要时说明不适用场景和边界。

不要机械地为每节凑齐四段。简单问题可以一段答完，复杂判断才展开。

### 4.5 决策或应用章节

信息型文章在结尾前应帮助用户把信息应用到自身情况。根据主题选择：

- How to choose
- Is it worth it?
- Who is this best for?
- Which option should you choose?
- Common mistakes
- When to contact a professional

如果加入这一章，它应尽量提供条件化判断或可执行方法，而不是简单重复前文。

### 4.6 FAQ

FAQ 是可选模块，不是每篇文章的固定装饰。

使用条件：

- 研究材料、PAA 或次关键词中存在重要补充问题。
- 问题与主意图直接相关，但放入主体会打断文章结构。
- 答案没有在正文中被完整回答。

建议：3-6 个问题，每个英文回答约 `40-80` 词。

回答规则：

- 第一句直接回答 `Yes`、`No`、范围、条件或做法。
- 后续只补充必要解释和例外。
- 不用 FAQ 重复正文来增加字数或关键词出现次数。

### 4.7 结论

建议英文长度：`80-150` 词。

如果文章需要独立结论，可以：

1. 摘要重申主问题的答案，不重新展开正文已完成的论证。
2. 总结最重要的选择条件。
3. 在存在真实下一步时提供一个自然行动。

结论通常不引入新的产品、数据、论点或未经解释的建议。短文章或答案已经自然收束时，可以不设独立结论。

## 5. 分类型文章骨架

### 5.1 Explanation Guide

适用于回答“是什么”“为什么”“如何运作”以及帮助读者理解一个主题。没有真实决策需要时，不强行加入优缺点或“是否值得”。

```text
H1: [主问题或主题] + [适用范围]
Direct answer
Key takeaways（仅在有多个重要结论时）
H2: 定义或理解答案所需的背景
H2: 工作原理、关键因素或形成原因
  H3: 必要的组成部分或子问题
H2: 这对读者意味着什么 / 如何应用
H2: 限制、例外或常见误解（仅在需要时）
H2: FAQ（仅在需要时）
Conclusion
```

写作要求：

- 开头先回答概念或因果问题，不用定义和历史拖延答案。
- 背景只保留理解答案所必需的信息。
- 将原理与用户影响连接起来，不停留在术语罗列。

### 5.2 Pros and Cons / Is It Worth It

适用于分析利弊并帮助用户判断某个方案是否适合，而不是所有 `Guide` 的固定骨架。

```text
H1: [主问题或主题] + [适用范围]
Direct verdict
Pros/Cons at a glance（仅在能提高扫描效率时）
H2: 理解判断所需的关键背景
H2: 主要优势、收益或支持理由
  H3: 每个独立优势或理由
H2: 主要缺点、成本或风险
  H3: 每个独立缺点或风险
H2: 是否值得 / 适合谁 / 不适合谁
H2: FAQ（仅在需要时）
Conclusion
```

写作要求：

- 开头先给总体判断，不让读者等到结尾才知道答案。
- 优点和缺点使用相同判断深度，不把缺点写成象征性一句话。
- 最终判断采用“总体结论 + 适用条件 + 不适用条件”。

### 5.3 How-To

适用于用户需要完成明确任务或解决具体问题。

```text
H1: How to [完成结果]
Direct answer + 预计结果
Requirements / Before you start
H2: Step-by-step process
  H3: Step 1...
  H3: Step 2...
  H3: Step 3...
H2: How to verify the result
H2: Common mistakes or troubleshooting
H2: FAQ（仅在需要时）
Conclusion / next action
```

写作要求：

- 每个步骤以动作动词开头。
- 步骤中说明输入、动作和预期结果。
- 步骤数量由任务决定，不强行凑成固定数字。
- 涉及风险、费用、数据丢失或不可逆操作时，在动作之前给出警告。
- 最好告诉用户如何判断任务已经成功；如果结果本身显而易见，可以不单独增加验证章节。

### 5.4 Comparison

适用于比较两个或多个明确选项。

```text
H1: [A] vs [B]: Which Is Better for [use case]?
Direct verdict + 条件
Comparison table
H2: How the options differ
H2: [统一比较维度 1]
H2: [统一比较维度 2]
H2: [统一比较维度 3]
H2: Choose A if...
H2: Choose B if...
H2: FAQ（仅在需要时）
Conclusion
```

写作要求：

- 关键选项应尽量使用一致的核心比较维度；必要时可以补充某个选项特有、且会影响决策的信息。
- 顶部先给条件化结论，不使用永远正确的单一胜者。
- 区分事实差异和作者判断。
- 不把品牌知名度、联盟佣金或资料数量当作产品优势。

### 5.5 Listicle / Best X

适用于用户希望快速找到适合某种场景的候选项。

```text
H1: Best [category] for [audience/use case]
Direct answer + 选择范围
Top picks comparison table
H2: Best for [scenario 1]: [item]
H2: Best for [scenario 2]: [item]
H2: Best for [scenario 3]: [item]
H2: How we evaluated the options
H2: How to choose the right option
H2: FAQ（仅在需要时）
Conclusion
```

为了便于比较，候选项通常可以使用相近的核心字段：

1. 适用场景和一句话结论。
2. 为什么入选。
3. 支持判断的关键事实或规格。
4. 明确限制、代价或不适用边界。

以下字段只在能帮助用户决策时使用，但同一篇文章中的候选应保持一致：

- 实际好处。
- Pros/Cons。
- 价格、规格或替代项。
- 适合谁、不适合谁。

单项参考英文长度：`250-450` 词。简单选项可以更短，复杂选项可以更长；字段可以根据候选特点调整，只要比较仍然公平、清楚。

写作要求：

- “Best”最好对应明确场景，避免多个候选共享含糊标签。
- 没有足够证据时减少候选数量，不用弱选项凑数。
- 有评测或排名时，建议说明数据来源、入选标准和限制。
- 当前运行时最多接受 12 个顶层 section。这是数据结构限制，不是好文章的通用标准。候选较多时，可以在一个或数个 `body_list` section 中用 H3 组织多个候选。

### 5.6 Review

适用于判断一个明确产品或服务。

```text
H1: [Product] Review: Is It Right for [audience]?
Verdict
Key facts / rating table
H2: Who it is for and who should skip it
H2: Evaluation method or evidence basis
H2: Performance by important use case
H2: Pros and cons
H2: Price and value
H2: Alternatives
H2: FAQ（仅在需要时）
Conclusion
```

写作要求：

- 没有实际测试时，不使用“我们测试发现”等第一手措辞。
- 明确区分厂商声明、第三方证据和作者判断。
- 替代项只比较影响购买决定的差异。

### 5.7 Directory / Local

只在拥有真实、可更新的实体数据时使用。

```text
H1: Best / Top [providers] in [location]
Data freshness and ranking disclosure
Provider table or list
H2: How providers were selected or ranked
H2: How to choose a provider
H2: Licenses, certifications, reviews and warranty checks
H2: How to compare quotes
H2: FAQ
Next action
```

写作要求：

- 页面主要价值来自数据覆盖和筛选，不靠增加说明文字制造长度。
- 评分最好同时显示样本量、更新时间和评分来源；缺少某项时应避免让评分显得比证据更确定。
- 明确商业关系以及公司是否可以付费影响排名。
- 没有完整数据时明确标注覆盖边界，不能把当前分页数据说成全部结果。
- `Directory` 是独立页面模板。普通文章生成链只负责可序列化的介绍、分类说明和实体文字内容；搜索、地区、分类、筛选和排序控件由页面应用及实体数据层实现，不能要求 Markdown 章节生成器伪造交互能力。

## 6. 字数和段落规则

字数是规划范围，不是质量目标。先覆盖问题，再确定长度。

### 6.1 英文段落

- 常规段落建议 `25-50` 词。
- 复杂解释可以达到 `50-70` 词。
- 超过 70 词时检查是否包含两个以上信息任务。
- 一个段落只表达一个核心意思。
- 连续三个以上长段落时，检查是否应加入小标题、列表或表格。

### 6.2 章节和全文

| 内容单元 | 建议英文词数 |
| --- | ---: |
| 导语和直接答案 | 100-180 |
| 快速答案模块 | 60-150 |
| 单个普通 H2 | 150-350 |
| 单个优点、缺点或比较维度 | 70-150 |
| 单个产品/服务评估 | 250-450 |
| 选购或决策章节 | 250-450 |
| 方法论章节 | 150-250 |
| 单个 FAQ | 40-80 |
| 结论 | 80-150 |

上表只是写作规划参考，不用于判断文章是否合格。实际长度由问题复杂度、证据量和读者需要决定。当前运行时要求顶层 `OutlineSection.word_target` 使用 `100-1,200` 的整数，这是数据结构兼容要求，不代表对应章节实际必须写满，也不限制 H3、单个 FAQ、列表项或段落的长度。

全文初始规划范围：

| 文章类型 | 常见英文词数范围 |
| --- | ---: |
| Guide | 1,400-2,400 |
| How-To | 1,200-2,200 |
| Comparison | 1,500-2,600 |
| Listicle / Best X | 由候选数量决定，通常 2,000-4,000 |
| Review | 1,500-2,500 |
| Directory / Local | 500-1,200 说明正文 + 实体数据 |

以下情况允许更短：问题简单、证据有限、答案无需多个章节。以下情况允许更长：候选项多、操作复杂、政策因地区不同、需要完整风险说明。

不要为了达到总字数重复结论、扩写定义、增加无关历史或添加重复 FAQ。

## 7. 表格、列表和格式规则

### 使用表格

只有需要按统一字段比较多个对象时使用表格，例如：

- 产品规格
- 价格或计划
- 优缺点
- 步骤输入和输出
- 服务商评分

表格中的列应尽量帮助用户作出判断。不要把长篇解释塞入表格。

### 使用列表

并列、可独立扫描的信息使用列表，例如：

- Key takeaways
- 前置条件
- 优点和缺点
- 常见错误
- 选择标准

如果列表项需要多段解释，改用 H3 小节。

### 使用加粗

只强调结论、关键数字或风险。不要在每段中机械加粗主关键词。

## 8. 证据和可信度规则

以下内容原则上需要可追溯证据，尤其是它们会影响用户决策时：

- 数字、比例、价格和时间。
- 性能、寿命、兼容性和产品规格。
- 法律、政策、税务、健康和安全判断。
- 市场规模、趋势和排名。
- “最佳”“最快”“最便宜”等相对或最高级结论。
- 研究结论、专家意见和用户评价汇总。

使用证据时：

1. 只使用资料实际支持的范围。
2. 说明适用国家、地区、时间和条件。
3. 优先使用官方文档、政府、原始研究和可核验的一手资料。
4. 引用竞争文章时，只把它当作线索；关键事实尽量回到原始来源核验。
5. 不把相关性写成因果关系。
6. 不把厂商宣传写成独立测试结论。
7. 无法核验的精确数字宁可删除，不用看似合理的数字填空。

关键小节可以根据任务选择回答：

- 事实是什么？
- 证据支持到什么程度？
- 这对用户意味着什么？
- 有什么限制？

普通解释性文字可以使用稳定的常识，但不得与提供的证据冲突，也不得伪造具体事实。数字、时效性、风险性、比较性、产品性以及其他会影响用户决策的外部事实，应由输入证据支持并保持其适用范围；证据不足时应降低确定性、说明边界或删除具体断言。

## 9. SEO 规则

- 主关键词应自然出现在 H1、导语或直接答案中，但不要求使用固定次数。
- 次关键词只在回答对应子问题时使用。
- 同义词和自然语言优先，不重复完整关键词破坏可读性。
- 重点问题最好有清楚的主要回答位置，避免多个章节重复展开；简单问题可以直接在导语回答，相关问题也可以合并到同一章节。
- Meta title 说明主题和区别点，不使用无法兑现的承诺。
- Meta description 说明读者将得到的答案，不堆关键词。
- 内链应帮助读者理解下一步，锚文本描述目标内容。
- 外链用于核验事实，不链接与论点无关的权威网站来制造可信感。

## 10. 品牌和 CTA 规则

- 通用信息文章默认保持中立。
- 只有项目产品、服务或工具直接解决当前问题时才加入品牌内容。
- 品牌信息必须来自项目的可核验资料。
- 不把品牌强行加入每个章节。
- 不虚构品牌功能、客户结果、价格或可用地区。
- CTA 应是读者完成当前任务的自然下一步。
- 一篇普通信息文章通常只需要一个主要 CTA。
- CTA 不得替代答案，也不能在文章尚未建立价值前打断阅读。

## 11. 底线与常见低质量写法

以下属于交付底线：

- 不编造第一手测试、访谈、客户案例、专家身份、来源、产品能力或具体数据。
- 不把来源未支持的高影响结论写成确定事实。
- 不省略危险操作所必需的安全警告。
- 不违反用户明确锁定的标题、文章类型或写作方向。
- 不从竞争文章复制句子、段落或独特表达。

以下是常见低质量倾向，应结合上下文判断，不作为机械拒绝条件：

- 不以“在当今快速发展的世界中”等空泛背景开头。
- 不用长篇定义回答一个本可直接回答的问题。
- 不重复标题、导语、Key Takeaways 和结论中的同一句话。
- 不为每个 H2 使用完全相同的句式。
- 不使用没有解释的形容词，如 powerful、revolutionary、seamless、game-changing。
- 不为满足 SEO 强行插入不相关关键词。
- 不为满足模板强行添加 FAQ、表格、优缺点或 CTA。
- 不把“可能”“通常”“取决于”当作逃避明确回答的方式；证据允许时应尽量给出条件化结论。

## 12. 四阶段生成指令

以下指令可分别用于现有的计划、章节写作、全文统一和质量检查阶段。变量名应映射到项目实际数据字段。除真实性、证据边界、必要安全警告和用户明确锁定要求外，其中的编号条目都是帮助模型提高成稿质量的默认做法，可以根据主题和读者任务调整。

### 12.0 阶段间参考信息

各阶段收到的上下文越完整，越容易应用本模板：

- 计划阶段可以使用第 2.3 节中当前可获得的输入。
- 章节写作阶段适合接收该 section 的目标、重点问题、覆盖点、证据、链接和参考字数；缺失字段不代表章节不能写作。
- 全文统一阶段适合接收计划、锁定要求、证据边界和全部章节正文。
- 质量检查阶段适合接收计划、证据边界和统一后的全文。

当前运行时只需使用实际获得的信息。模板不要求每个字段都存在，也不要求为满足模板而补造内容。

### 12.1 计划阶段

```text
Create an article plan that completely resolves the reader's primary task.

1. Identify one primary article type from Guide, How-To, Comparison, Listicle,
   Review, or Directory. Respect a locked article type.
2. State the search intent as the decision, action, or understanding the reader
   needs to complete.
3. Give the direct answer before background information.
4. Give important reader questions a clear place in the article. A simple question
   may be answered fully in the introduction, and closely related questions may
   share a section. Avoid unnecessary duplication across sections.
5. Choose only the structural modules needed for this article type.
6. For each section, define its objective, questions, coverage points, evidence
   requirements, and a word target based on complexity.
7. Include a decision or application section when the reader must choose or act.
8. Include FAQs only for important unanswered questions.
9. Do not invent claims, sources, products, tests, or local entities.
10. Do not force project branding or a CTA unless it directly helps answer the
    reader's question and verified project facts are available.
11. Stay within the runtime limit of 12 top-level sections. Within that limit,
    use as many or as few sections as the topic needs.
12. Treat word targets as ranges for complete coverage, not quotas to fill.
```

### 12.2 章节写作阶段

```text
Write only the assigned article section.

1. Fulfill the section objective and answer every required question assigned to it.
2. Start with the section's answer or practical conclusion.
3. Use supplied evidence for numeric, time-sensitive, risky, comparative,
   product-specific, and other decision-relevant external claims. Stable general
   explanations must not conflict with the evidence or invent specific facts.
   Preserve the evidence's scope, date, market, and limitations.
4. Explain what each important fact means for the reader; do not list facts
   without interpretation.
5. Use one idea per paragraph. For English, prefer 25-50 words per paragraph and
   split paragraphs that perform multiple jobs.
6. Use a table only for consistent comparisons and a list only for parallel,
   scannable items.
7. State meaningful tradeoffs and limits. Do not write promotional copy.
8. Add only the assigned internal links and use descriptive anchor text.
9. Do not repeat material covered by previous section summaries.
10. Do not add an introduction, conclusion, FAQ, CTA, or new heading unless the
    section plan requires it.
11. Do not mention the writing process, prompt, sources pack, SEO instructions,
    or word target in the article.
```

### 12.3 全文统一阶段

```text
Edit the assembled article into one coherent final draft.

1. Preserve supported facts, citations, required answers, locked requirements,
   and valid links.
2. Remove repeated explanations, duplicated conclusions, and redundant FAQs.
3. Make the direct answer clear near the beginning and the final recommendation
   consistent with the evidence.
4. Keep terminology, tense, point of view, units, capitalization, and product
   names consistent.
5. Improve transitions only where the logic would otherwise be unclear.
6. Keep headings specific and make the outline understandable when scanned alone.
7. Do not introduce new claims, products, links, examples, or recommendations.
8. Do not expand the article merely to reach a word count.
9. Keep brand mentions and CTAs only where they are relevant and verified.
10. Return the complete article with its original section identities intact.
```

### 12.4 质量检查阶段

```text
Evaluate whether the article usefully and honestly resolves the reader's task.

Block delivery only for material trust problems:
- Invented facts, sources, products, entities, tests, or first-hand experience.
- Decision-relevant external claims that materially exceed the supplied evidence.
- Dangerous instructions that omit necessary risk warnings.
- Direct contradiction of locked user requirements.
- Copied sentences, paragraphs, or distinctive wording from competitor articles.

Treat all other observations as improvement suggestions, not automatic failures.
Examples include a slow opening, an unanswered secondary question, repeated
sections, uneven comparisons, an unnecessary FAQ, weak transitions, unusual
length, or a structure that differs from the suggested article-type outline.

Do not reject an article solely because it differs from this template, falls
outside a suggested word range, combines sections, omits a conclusion, FAQ,
table, CTA, or quick-answer block, or uses a different heading sequence.

For each material issue, identify the affected section and the smallest useful
repair. Do not rewrite unaffected sections.
```

## 14. 发布前自查提示

以下问题用于发现改进机会，不要求全部勾选。某项不适用于当前文章时可以直接跳过；未勾选也不自动代表文章不能发布。只有真实性、证据边界、必要安全警告、原创性和用户明确锁定要求等底线问题才需要阻止交付。

### 用户任务

- [ ] 前 1-3 句直接回答了主问题。
- [ ] 重点问题已有清楚答案，没有因模板拆分而产生不必要重复。
- [ ] 文章结束时，读者知道下一步如何判断、选择或行动。

### 结构

- [ ] 文章有清楚的主要逻辑，混合结构没有造成阅读混乱。
- [ ] 每个章节有清楚重点，相关任务的合并是自然的。
- [ ] 标题序列本身能够说明文章逻辑。
- [ ] 没有为关键词变体建立重复章节。
- [ ] FAQ 没有重复正文。

### 证据

- [ ] 数字、价格、日期、政策、规格和性能有来源。
- [ ] 影响决策的外部事实都没有超出来源支持范围，普通解释也没有与证据冲突。
- [ ] 没有虚构测试、实体、评价或客户结果。
- [ ] 时效信息说明了适用时间和市场。

### 决策价值

- [ ] 不只列事实，还解释了对用户的意义。
- [ ] 明确说明重要限制和不适用情况。
- [ ] 比较文章对关键选项使用了足以公平比较的核心维度，并合理处理选项特有信息。
- [ ] 推荐文章说明了每个候选的入选原因和取舍。
- [ ] 操作文章说明了前置条件、步骤结果和验证方式。

### 表达和 SEO

- [ ] 段落主要是一个信息单元，没有连续大段堆积。
- [ ] 没有空泛开场、重复总结或为了字数填充的内容。
- [ ] 主关键词和次关键词自然出现，没有固定密度要求。
- [ ] 表格、列表、加粗和链接都承担明确用途。
- [ ] 品牌和 CTA 与当前用户问题直接相关。

## 15. 期望效果

文章生成流程参考本模板后，期望更常出现以下结果，但不要求每篇文章逐项满足：

1. 同一输入重复规划时，文章类型和核心问题覆盖基本稳定。
2. 不同文章类型产生不同的合理骨架，而不是相同大纲换标题。
3. 重点问题能在文章中找到清楚答案，导语、正文和结论没有机械重复。
4. 关键事实能追溯到证据，不支持的事实不会进入文章。
5. 全文不存在明显重复章节、凑字数段落和重复 FAQ。
6. 文章先解决用户问题，再承载 SEO、内链和转化目标。
