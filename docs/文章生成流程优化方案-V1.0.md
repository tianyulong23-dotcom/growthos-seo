# 文章生成流程优化方案 V1.0

## 1. 结论

后端应固定为以下流程：

```text
项目资料快照
-> SERP、站内资料并行收集
-> 抓取竞品正文
-> AI 首次规划：主问题、大纲、关键资料缺口
-> 有关键缺口：并行补研究 -> AI 用新资料重新规划
-> 无关键缺口：直接使用首次规划
-> AI 一次生成完整文章
-> AI 一次完成全文通读、纠偏和改写
-> 程序检查格式、链接、章节和文档结构
-> 保存文章
```

核心原则：

- 研究不够时继续找资料，不能直接带着缺口写。
- 补到新资料后必须重新规划，不能继续使用旧大纲。
- AI 检查必须返回已经改好的全文，不能只返回问题清单。
- 质量问题按根因回到对应阶段，不能对同一篇文章反复做无方向的重写。
- 保留 Temporal、DataForSEO 缓存、对象存储和类型化输出，不引入第二套工作流。

## 2. 当前问题

| 问题 | 当前代码 | 后果 |
|---|---|---|
| 补研究后没有重新规划 | `generation.py::plan_article()` 更新了 `pack`，最后仍执行 `normalize_plan(raw_plan, pack)` | 新资料没有改变主问题、大纲和章节任务 |
| 补研究失败仍继续写 | `plan_article()` 只追加 `supplemental_research_degraded` | 核心答案缺资料时也会生成空泛正文 |
| 写作阶段职责混乱 | `write_article_sections()` 实际用 `unify_article` 调用名一次写全文 | 调用记录难以区分“写作”和“编辑” |
| 质量循环不修改文章 | `_apply_content_quality_loop()` 只评分并返回原稿 | 低质量、重复或跑题只能被记录，不能被修正 |
| 主工作流不执行修订 | `ArticleGenerationWorkflow.run()` 只执行一次 `checking_1`；`_run_with_quality_revisions()` 未被调用 | 已有 `revise_article_sections()` 没进入正式链路 |
| 检查范围过窄 | `check_article()` 的正常修复范围主要覆盖 `fallback_section` | 跑题、重复、空话和结构问题无法正确路由 |

## 3. 逐步骤代码对齐

| 步骤 | 对齐项目及具体做法 | `seo-main` 代码改动 | 验收 |
|---|---|---|---|
| 1. 冻结本次任务输入 | **seo-main**：继续使用 Temporal 运行、项目快照和阶段产物 | 保留 `workflows.py::ArticleGenerationWorkflow`、`collection.py::prepare_project()`；在运行产物中冻结关键词、标题要求、项目资料版本和 SERP 请求参数 | 重试同一个 `run_id` 不改变文章题目和项目资料 |
| 2. 并行收集 SERP 和站内资料 | **GPT Researcher**：独立研究分支有限并发、单支失败不丢失成功结果；**seo-main**：DataForSEO 账本和缓存复用 | 保留 `collection.py::collect_sources()` 的并行结构；继续由 `dataforseo.py` 判断缓存和真实请求；每个来源保存状态和失败原因 | 相同 SERP 参数命中缓存时 DataForSEO 新请求数和费用为 0；单个站内来源失败不重跑 SERP |
| 3. 抓取竞品正文 | **GPT Researcher**：来源独立抓取和失败隔离；**seo-main**：普通抓取失败后切换 rendered 模式 | 保留 `collection.py::collect_competitors()`、`_run_crawl()`、`_prefer_pages_with_body()`；按 SERP 排名依次补位，不另搜无关 URL | 至少记录正文成功数、失败数、最终 URL、抓取模式和 `html_ref`；普通模式失败会尝试 rendered 模式 |
| 4. AI 首次规划 | **STORM**：研究材料先形成大纲，规划产物单独保存；**claude-blog**：先锁定读者真正要完成的任务，再设计直接回答问题的 H2 | 保留 `generation.py::plan_article()`，让 `ArticlePlan` 明确输出 `main_question`、直接可用的 H2、每节目标、覆盖问题、目标字数、claims 和 `critical_research_gaps`；规划结果写入独立 artifact | H2 是文章中的真实标题，不是“介绍/讨论/说明如何写”；每节有内容目标和字数 |
| 5. 判断关键资料缺口 | **STORM**：研究结果反过来影响规划；**claude-blog**：只把阻止核心答案成立的缺口视为关键缺口 | 继续使用 `CriticalResearchGap`，但每个 gap 必须含 `missing_information`、`why_it_blocks_core_answer`、`research_query`；最多 4 个，合并同一主题的小问题 | 可选统计、装饰性案例或非核心品牌信息不会触发补研究；核心比较依据缺失会触发 |
| 6. 并行补研究 | **GPT Researcher**：`Semaphore + gather`、有限并发、分支失败隔离、相关上下文筛选 | 把 `plan_article()` 中直接调用 `_collect_research()` 的逻辑移到独立 `supplemental_research` activity；复用 `collection.py::_collect_research()`、`research_gateway.py::research()` 和 `_verify_research_sources()` | 最多 4 个完整问题并行执行；180 秒总上限；成功结果独立持久化，超时分支不抹掉成功分支 |
| 7. 用新资料重新规划 | **STORM**：阶段产物可重新载入，新增证据必须进入后续大纲；不是照搬 STORM 文件系统 | 新增 `generation.py::replan_article()`；输入首次计划和更新后的 research pack，再调用 `WritingGateway`；只有确实新增资料时运行；输出 `planning_final/plan.json.gz` | 补研究成功后出现第二次规划调用；最终大纲能引用新增证据；禁止继续 normalize 旧 `raw_plan` |
| 8. 一次生成完整文章 | **claude-blog**：完整 editorial brief 驱动文章；**seo-main**：继续使用结构化 `UnifiedArticle` 和请求缓存 | `write_article_sections()` 保持一次全文调用，但调用名改为 `write_full_article`；输入只使用最终 `ArticlePlan`、相关证据、项目资料和内部链接；输出必须按计划返回全部 `section_id` | 每个计划章节恰好出现一次；缺章节或章节无正文属于技术失败并按同一幂等键重试，不用 fallback 空话补齐 |
| 9. AI 通读并直接改好全文 | **claude-blog**：最终 editorial pass；AI 发现重复、跑题、空话、衔接和答案不足后直接修改 | 保留 `generation.py::unify_article()`，改名或明确职责为 `review_and_revise_article()`；一次调用同时检查和输出修改后的 `UnifiedArticle`，不单独输出只读问题报告；锁定主问题、用户指定标题和 `section_id` | 输入原稿，输出完整改稿；测试必须证明重复段落被删除、跑题内容被改回、核心问题仍在正文中得到直接回答 |
| 10. 程序检查并保存 | **SEO Machine**：只借鉴可确定计算的标题、链接和结构测量；**seo-main**：文档、资产、发布前一致性检查 | `check_article()` 只负责可确定检查：章节完整、Markdown/文档可解析、链接格式、内部 URL、资源引用；语义问题不在这里反复猜测。通过后由 `content_finish_run` 保存 | 检查失败能定位字段或章节；保存失败重试不重新调用 AI；最终文章与检查通过的 artifact 哈希一致 |

## 4. 后端修改清单

### 4.1 `backend/api/app/modules/content/writing_gateway.py`

修改类型：

```python
class ArticlePlan(BaseModel):
    main_question: str
    title: str
    search_intent: str
    article_type: str
    total_word_target: int
    claims: list[EvidenceClaim]
    sections: list[OutlineSection]
    contract: ArticleContract
    critical_research_gaps: list[CriticalResearchGap]

WritingCall = Literal[
    "plan_article",
    "replan_article",
    "write_full_article",
    "review_and_revise_article",
]
```

`OutlineSection` 至少保留：

```text
section_id、heading、objective、required_questions、coverage_points、word_target、claim_ids、cta_type
```

删除正式流程中不再使用的调用类型时，只删除由本次流程替换后确认无引用的项，不清理其他编辑器功能。

### 4.2 `backend/api/app/modules/content/generation.py`

1. `plan_article()` 只生成并保存首次计划，不在函数内部执行补研究。
2. 新增 `research_needed(plan) -> bool`，只判断是否存在真正阻塞核心答案的 gap。
3. 新增 `replan_article()`：

```text
输入 = 首次计划 + 更新后的 research pack + 新增来源 ID
输出 = 最终 ArticlePlan
规则 = 可重做主问题和大纲；不得为了塞入资料扩展成无关主题
```

4. `write_article_sections()` 改为明确的 `write_full_article()`，仍只调用一次模型。
5. `unify_article()` 改为 `review_and_revise_article()`，模型必须返回修改后的全文。
6. 删除 `_apply_content_quality_loop()` 在正式链路中的空评分调用；`ContentScorer` 作为观测数据，不作为自动接受劣稿的理由。
7. 保留 `cached_generate()`；其请求键继续由 `run_id`、`step_key`、`repair_iteration`、`call_type` 和完整 `payload` 共同计算，保证同一阶段同一输入重试时复用成功结果。

### 4.3 `backend/api/app/modules/content/activities.py`

目标映射：

```python
handlers = {
    "planning": plan_article,
    "supplemental_research": collect_supplemental_research,
    "replanning": replan_article,
    "writing": write_full_article,
    "editing": review_and_revise_article,
    "checking": check_article,
}
```

`collect_supplemental_research` 负责调用现有 `_collect_research()`，不要在 activity 中再创建一套研究客户端。

### 4.4 `backend/api/app/modules/content/workflows.py`

不要继续使用固定 `ARTICLE_STAGES` 循环表达条件分支。按以下依赖显式调度：

```text
preparing -> collecting -> competitor_research -> planning
planning.research_needed = false -> writing
planning.research_needed = true  -> supplemental_research
supplemental_research.added_count > 0 -> replanning -> writing
supplemental_research.added_count = 0 -> 关键缺口仍存在则失败，不生成空话稿
writing -> editing -> checking_1 -> finalizing
```

取消通用的多轮语义重写循环。只保留：

- 模型超时、429、临时 5xx、结构化输出失败：同阶段有限技术重试。
- 保存失败：只重试保存。
- 确定性格式错误：定点修复后再检查一次。
- 主问题、大纲、重复、跑题：分别回到规划或全文编辑，不进入无方向循环。

### 4.5 `backend/api/app/modules/content/collection.py`

- 复用 `_collect_research()` 和 `_verify_research_sources()`。
- 补研究输入只接受计划产出的完整 query，不再让研究层把一个问题拆成 7 个问题。
- 每个结果保存 `query`、状态、来源 URL、摘录、核实状态、耗时和错误码。
- 同一品牌的多个事实请求先合并成一个品牌研究任务，再在结果中拆 evidence，减少超时和调用数。

## 5. 问题路由

| 发现的问题 | 回到哪里 | 允许次数 |
|---|---|---|
| 核心事实缺失 | `supplemental_research -> replanning` | 一批，最多 4 个合并问题 |
| 主问题理解错、偷偷换题 | `replanning` | 1 次 |
| 大纲跑偏、H2 只是写作说明 | `replanning` | 1 次 |
| 重复、空话、AI 腔、衔接差 | `editing`，直接输出改稿 | 1 次 |
| 章节缺失、JSON 不合法 | 当前 AI 阶段技术重试 | 最多 2 次 |
| Markdown、链接、文档结构错误 | 确定性修复和复检 | 1 次 |
| 数据库保存失败 | `finalizing` | 只重试保存，不重跑 AI |

## 6. 测试与验收

需要修改：

- `backend/api/tests/test_content_generation.py`
  - 补研究成功后必须调用 `replan_article`，最终计划使用新证据。
  - 补研究没有新增资料且关键缺口仍存在时，不进入写作。
  - 全文写作只有一次模型调用，全部 `section_id` 完整且有正文。
  - 编辑调用返回改稿，并实际删除重复、跑题和空话示例。
- `backend/api/tests/test_content_workflow.py`
  - 覆盖无缺口直达写作、有缺口研究后重规划、研究失败停止、保存失败只重试 finalizing。
  - 断言正式路径不进入无方向多轮 revision。
- `backend/api/tests/test_content_collection.py`
  - 覆盖品牌问题合并、最多 4 个任务、180 秒总预算、并发成功结果保留。
  - 覆盖 DataForSEO SERP 复用时不产生新请求。

最终验收标准：

1. 运行记录能看见首次计划、补研究、最终计划、全文初稿、全文改稿和最终检查各自产物。
2. 新资料加入后，大纲必须重新生成。
3. 文章质量问题被实际修改，而不是只显示 warning。
4. 同一输入重试复用已有 SERP、研究和模型成功结果。
5. `finalizing` 失败不会再次产生 DataForSEO 或模型费用。

## 7. 不做什么

- 不引入 STORM 或 LangGraph 替换 Temporal。
- 不恢复按章节多次生成作为默认路径。
- 不把竞品结构当作强制模板。
- 不把所有写作建议变成阻塞性质量规则。
- 不用反复重写全文掩盖研究或大纲阶段的问题。
