# 图片接入文章生成流程方案 V1.0

## 1. 结论

图片不能在文章写完后随机插入。图片计划应绑定最终大纲，图片获取与全文写作并行，最后由程序按稳定 ID 插入文章文档。

```text
最终文章计划（已包含图片计划）
-> 按图片用途选择：项目原图 / 产品截图 / 图表 / 正版图库 / AI 图片
-> 各图片并行获取
-> 全部进入现有 AssetService 处理
-> ready 后绑定 section_id 和 visual_id
-> 程序把 image 节点插入文章文档
-> 图片质量检查
-> 保存和发布
```

原则：

- 图片必须帮助用户理解、比较、验证或执行，不按“每个 H2 一张”凑数量。
- 真实产品状态优先用项目图片或真实截图，不能用 AI 图片冒充。
- AI 图片生成失败不能拖垮正文；用户明确指定的必需图片缺失才阻止完成。
- 不新建媒体库，复用现有上传、远程导入、安全检查、去重、变体、文章绑定和发布映射。

## 2. 逐步骤代码对齐

| 步骤 | 对齐项目及具体做法 | `seo-main` 代码改动 | 验收 |
|---|---|---|---|
| 1. 判断图片是否有价值 | **claude-blog** `Image Selection Rules`：图片必须回答、演示、比较、证明或帮助定位；不提供价值就不放 | 最终 `ArticlePlan` 增加 `visuals`；每项必须有 `reader_job`，不按章节数量自动生成 | `reader_job=decoration` 或无法说明用户价值的项被规划校验删除 |
| 2. 规划图片位置和类型 | **GPT Researcher** `image_generator.py::plan_and_generate_images()`：先输出 `title/prompt/section_hint`；**claude-blog**：优先截图、产品图、图表和流程图 | 将 GPT Researcher 的弱 `section_hint` 改成稳定的 `visual_id + section_id`；首次 `plan_article` 必须同时输出图片计划，有补研究时由 `replan_article` 随最终大纲重做，不增加单独 AI 调用 | 每张图绑定存在的 `section_id`；同一位置最多一张主图；输出包含尺寸、alt 写作要求、caption 和来源策略 |
| 3. 选择来源 | **claude-blog**：真实界面用截图，数据用图表，图库走官方 API 并保留许可信息，AI 只补无法获取的说明性画面 | 新增确定性 `choose_visual_strategy()`；AI 可以建议类型，但后端按 `reader_job`、是否真实产品状态、是否有数据和项目资产可用性确定最终 provider | 产品界面不会路由到 AI provider；有结构化数据的比较图不会路由到图库 |
| 4. 并行获取图片 | **GPT Researcher**：在写作前用 `asyncio.gather` 并行生成，单图失败返回空结果；**seo-main**：使用 Temporal 和有界并发 | 新增 `resolve_visuals()` activity；用 `Semaphore` 限制 2–4 个并发任务；图片获取可与 `write_full_article` 并行，二者都依赖最终计划 | 单图超时不取消其他图片和正文；每个 visual 独立记录 provider、attempt、耗时、费用和错误 |
| 5. 接入图片提供器 | **GPT Researcher**：图片生成器和文章写作器分离；**seo-main**：沿用现有网关隔离、幂等产物和 Temporal 技术重试方式 | 新增 `image_gateway.py` 的统一接口；项目资产、截图、图表、图库和 AI 分别实现 provider；provider 只返回二进制或可立即下载 URL 及来源元数据，不直接改文章 | 更换 AI 图片供应商不修改工作流、资产处理和文档插入代码 |
| 6. 注册到现有资产系统 | **seo-main**：现有 `AssetService.import_url()`、multipart upload、`AssetProcessingDispatcher`、安全检查、哈希去重和 variants | 远程 URL 调 `AssetService.import_url()`；在 `asset_service.py` 新增内部 `ingest_bytes()`，让截图、图表和 AI 图片复用相同的 `ContentAsset -> AssetProcessingJob` 链路，不模拟前端 multipart 请求 | 不允许工作流直接保存外部临时 URL；重复图片复用 canonical asset；不合规文件进入 failed/quarantined |
| 7. 绑定文章位置 | **GPT Researcher**：把图片元数据交给 writer；在本项目中改为程序绑定，避免模型编造 asset ID | 新增 `ResolvedVisual`，保存 `visual_id -> asset_id -> section_id`；正文 AI 只知道视觉用途，不输出真实 `asset_id`；通过现有 `ArticleAssetBinding` 建立引用 | 模型输出不能创建任意资产引用；跨项目或非 ready asset 绑定被现有数据库规则拒绝 |
| 8. 插入文章文档 | **SEO Machine**：只借鉴可检查的图片 marker/alt；**seo-main**：使用现有 `SectionDraft.section_id`、`document.py` image node 和 asset manifest | 新增 `visual_assembly.py::assemble_visual_document()`；逐个把 `SectionDraft.markdown` 转成节点，在匹配的 `section_id` 内插图后再合并文档；不能把全文先转 Markdown 再按标题猜位置；`node_id` 由 `visual_id` 确定 | 标题相同或编辑过也不会插错章节；相同输入重复执行不会插入两次；`extract_asset_manifest()` 与 `ArticleAssetBinding` 一致 |
| 9. 图片 QA | **claude-blog** `Media QA For Blog Posts`、`Alt Text Standards`、`Chart Source Requirements`：检查用途、alt、尺寸、图表来源和实际渲染 | 新增 `validate_article_visuals()`；检查 ready 状态、宽高、alt、重复图、位置、caption、许可/来源、图表数据来源；发布前继续使用现有 asset manifest 校验 | cover/正文图有尺寸；信息图 alt 非空；装饰图必须显式 `alt=""`；AI 图不会被标记为真实截图 |
| 10. 降级和完成 | **GPT Researcher**：图片失败返回空结果，不阻断文本报告 | optional 图片失败写 warning 并省略节点；required 只用于用户上传并锁定的图片，缺失时停止 finalizing；失败图片可后台重试后由编辑器补入 | AI/图库故障时文章正文仍完成；用户锁定图片缺失时错误能指出 `visual_id`，不重新生成文章 |

## 3. 数据结构

### 3.1 `backend/api/app/modules/content/writing_gateway.py`

新增：

```python
class VisualPlanItem(BaseModel):
    visual_id: str
    section_id: str
    reader_job: Literal["explain", "demonstrate", "compare", "prove", "orient"]
    source_strategy: Literal["project_asset", "screenshot", "chart", "stock", "ai"]
    required: bool = False
    title: str
    prompt: str | None = None
    alt_instruction: str
    caption: str | None = None
    aspect_ratio: Literal["16:9", "4:3", "1:1"] = "16:9"
    data_claim_ids: list[str] = Field(default_factory=list)

class ArticlePlan(BaseModel):
    # existing fields...
    visuals: list[VisualPlanItem] = Field(default_factory=list)
```

约束：

- `required=True` 只能来自用户锁定的项目资产，AI 自动建议的图片一律 optional。
- `source_strategy=screenshot` 必须关联项目页面或允许访问的目标 URL。
- `source_strategy=chart` 必须有 `data_claim_ids`，且这些 claim 能追溯到研究来源。
- `source_strategy=ai` 的 `reader_job` 不能是 `prove`，AI 图片不能作为事实证据。
- 规划阶段只写 `alt_instruction`；最终 `alt_text` 必须根据实际拿到的图片生成并检查，不能只复述 prompt。

### 3.2 新增 `backend/api/app/modules/content/image_gateway.py`

```python
class ImageRequest(BaseModel):
    run_id: str
    project_id: str
    visual: VisualPlanItem
    idempotency_key: str

class ImageResult(BaseModel):
    visual_id: str
    provider: str
    source_url: str | None
    content: bytes | None
    mime_type: str
    width: int | None
    height: int | None
    license_name: str | None
    creator_name: str | None
    attribution_url: str | None
    generation_request_id: str | None
    cost_usd: Decimal | None

class ImageProvider(Protocol):
    async def acquire(self, request: ImageRequest) -> ImageResult: ...
```

提供器：

```text
ProjectAssetProvider -> 查询当前项目已有 ready 资产
ScreenshotProvider   -> 捕获真实页面状态并保存原始 URL、时间和视口
ChartProvider        -> 根据已核实数据确定性渲染 PNG/WebP
StockProvider        -> 官方图库 API，保存许可、作者和来源页
AIImageProvider      -> 调配置的图片模型，保存 prompt、model、request_id 和费用
```

禁止 provider 直接写 `Article.document`。provider 只获取图片，资产服务负责存储，assembly 负责插入。

`ImageResult.content` 只允许在当前进程内短暂传给资产服务，不能写进 JSON artifact 或数据库。`register_image_result()` 必须立即执行以下二选一：

```text
source_url != null -> AssetService.import_url(...)
content != null    -> AssetService.ingest_bytes(...)
```

`AssetService.ingest_bytes()` 是需要新增的内部方法，职责只有：校验大小和声明 MIME、写入 incoming object、创建 `ContentAsset + AssetProcessingJob`。后续仍由 `AssetProcessingDispatcher` 完成 MIME 探测、安全检查、哈希去重和 variants。

### 3.3 新增 `backend/api/app/modules/content/visual_generation.py`

```python
class ResolvedVisual(BaseModel):
    visual_id: str
    section_id: str
    asset_id: str | None
    status: Literal["ready", "failed", "omitted"]
    required: bool
    alt_text: str
    caption: str | None
    provider: str
    failure_code: str | None

async def resolve_visuals(...): ...
async def register_image_result(...): ...
async def wait_for_ready_assets(...): ...
```

阶段产物保存到：

```text
article-runs/{run_id}/visuals/plan.json.gz
article-runs/{run_id}/visuals/{visual_id}/result.json.gz
article-runs/{run_id}/visuals/resolved.json.gz
```

幂等键：

```text
sha256(project_id + visual_id + provider + normalized_prompt + aspect_ratio)
```

命中成功产物或 canonical asset 时直接复用，不再次调用收费图片模型。

## 4. 工作流接入

### 4.1 `backend/api/app/modules/content/activities.py`

新增映射：

```python
"visual_resolving": resolve_visuals,
"visual_assembling": assemble_article_visuals,
"visual_checking": check_article_visuals,
```

### 4.2 `backend/api/app/modules/content/workflows.py`

最终计划完成后并行执行：

```text
branch A: write_full_article -> review_and_revise_article
branch B: resolve_visuals -> wait_for_ready_assets
join:     assemble_article_visuals -> check_article -> check_article_visuals -> finalizing
```

Temporal 规则：

- 每个 `visual_id` 是独立幂等单元，成功项恢复时不重跑。
- `resolve_visuals` 总超时与单 provider 超时分开配置。
- AI/图库图片最多 2 次技术重试；鉴权、内容策略拒绝、无许可信息不重试。
- optional 图片失败后 join 不等待；required 图片失败才阻止完成。
- `finalizing` 重试只保存 document 和 bindings，不重新获取图片。

## 5. 文档插入规则

新增 `backend/api/app/modules/content/visual_assembly.py`，不要让 AI 输出 `:::article-image` JSON。

```text
1. 读取编辑完成后的 `list[SectionDraft]`
2. 校验 visual.section_id 存在于最终计划和 SectionDraft
3. 逐节执行 markdown_to_document(section.markdown)
4. 在匹配 section 的第一个解释性段落后插入 image node
5. 按计划顺序合并各节 document.content
6. attrs.node_id = "visual:" + visual_id
7. attrs.asset_id = resolved asset_id
8. 写入最终 alt、caption、display
9. normalize_document() 和 extract_asset_manifest()
10. repository.update_article_document() 同步 bindings
```

image node 示例：

```json
{
  "type": "image",
  "attrs": {
    "node_id": "visual:visual-01",
    "asset_id": "asset-id",
    "alt": "用户可以从图片获得的信息",
    "caption": "必要的上下文或来源说明",
    "display": "wide"
  }
}
```

封面图与正文图分开：封面图使用独立 role；正文不得为了封面重复插入同一图片。

## 6. 失败与降级

| 情况 | 处理 |
|---|---|
| 项目已有合适图片 | 直接复用 ready asset，不调用外部 provider |
| 普通远程图片下载失败 | 同 provider 技术重试一次，之后尝试下一允许来源 |
| 图库无结果或许可不完整 | 不导入；可转 AI illustration，但不能替代真实产品截图 |
| AI 图片生成超时或拒绝 | 记录 warning，省略 optional 图片，正文继续 |
| 图片处理 failed/quarantined | 不插入文章；保留资产错误码供后台诊断 |
| 图片未 ready 到达总时限 | optional 省略；required 终止 finalizing |
| alt 或 section_id 不合法 | 规划产物校验失败，修复图片计划，不重写正文 |
| 文章保存失败 | 复用 resolved asset 和 document artifact，只重试保存 |

## 7. 测试与验收

新增：

- `backend/api/tests/test_content_visual_generation.py`
  - provider 路由、有限并发、幂等缓存、单图失败隔离、费用记录。
  - 产品截图不落入 AI provider；AI 图不允许 `reader_job=prove`。
- `backend/api/tests/test_content_visual_assembly.py`
  - 按 `SectionDraft.section_id` 稳定插入；两个相同 H2 也不会插错；重复执行不重复节点；缺失 optional 图片不生成空节点。
  - `extract_asset_manifest()` 与 `ArticleAssetBinding` 一致。
- 扩展 `backend/api/tests/test_content_asset_service.py`
  - `import_url()` 和新增 `ingest_bytes()` 都进入现有处理、去重和 variants 链路；大文件、伪 MIME 和重复字节按现有规则处理。
- 扩展 `backend/api/tests/test_content_workflow.py`
  - 正文与图片并行；optional 图片失败仍完成；required 图片失败停在 visual finalization；保存重试不重复收费。
- 继续使用 `backend/api/tests/test_article_document.py`
  - alt、image node、HTML 渲染和 asset manifest 回归。

最终验收标准：

1. 每张图都能回答“为什么放在这里”。
2. 图片计划绑定最终大纲，不靠模型猜插入位置。
3. 所有图片都成为项目内 `ContentAsset`，文章不保存临时外链。
4. AI 图片失败不影响正文完成，用户锁定图片除外。
5. 发布时图片 URL、alt、尺寸、许可/来源和 WordPress media mapping 可追踪。

## 8. 不做什么

- 不声称 STORM 有完整图片生成流程；本方案图片部分不对齐 STORM。
- 不按固定密度强塞图片。
- 不让 AI 图片冒充真实产品、截图、数据或证据。
- 不让写作模型生成真实 `asset_id`。
- 不绕过现有 AssetService 直接保存第三方 URL。
- 不因为 optional 图片失败重新生成整篇文章。
