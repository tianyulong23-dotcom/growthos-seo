## 2. Compatibility Decision

The integrated `john3947-seo-main` repository is the final coding base.
The legacy `john3947-seo` repository is used only to recover missing Backlinks
contracts and compare behavior.

The coding strategy is:

```text
preserve integrated Platform Project, SiteProfile, Keyword, Content, Audit,
GSC, crawler, and agent modules
-> add Backlinks-specific contracts at explicit boundaries
-> prove project/data contract and routing compatibility
-> prove additive persistence and migration compatibility
-> prove integrated runtime compatibility
-> repair Recommendation, AI Draft, Gmail, and Send/Sync one vertical at a time
```

The following approaches are prohibited:

- replacing the integrated Project system with the legacy Project module;
- copying the legacy repository over `main`;
- mounting the legacy Backlinks `ProjectWorkspace` as a second production
  project-management entry;
- letting Backlinks query colleague-owned internal tables directly;

  mainline reconciliation phases pass;
- changing multiple phases in one coding task;
- treating builds, HTTP `200`, Mock UI, or generated clients as product
  acceptance.

## 3. Product Data Model

The product uses one Project and one shared SEO fact base with separate
authorities:

| Authority | Owns |
|---|---|
| Platform Project | Tenant identity, root Project ID, domain, lifecycle |
| SiteProfile/versions | Machine-discovered website facts |
| Keyword/Content/Audit/GSC modules | Keyword, competitor, SERP, content, audit, and search evidence |
| ProjectOutreachProfile/version | User-confirmed Backlinks goals and matching inputs |
| Backlinks | Candidate qualification, accessibility, cooperation path, contact, recommendation, outreach, reply lineage, and placement evidence |

### 3.1 Canonical Project Entry

The integrated production UI has one Project-management model:

```text
/projects
-> list, create, archive, restore, and enter a Platform Project

/projects/:projectId/...
-> exact active Project context shared by every SEO and Backlinks module
```

The App Shell may provide a convenient Project switcher, but it uses the same
Platform Project API and route identity. Backlinks does not add a second
`网站项目` tab or create a separate Website Project record.

The legacy Backlinks Project workspace is source material only. Its useful
archive/restore, switching, profile-editing, and recovery behavior is ported
into the global Project center and Project settings. The integrated
`CreateProjectDialog` and business-profile onboarding remain the creation
flow. Backlinks-specific goals are saved as a versioned
`ProjectOutreachProfile`, not as another Project.

Backlinks consumes upstream facts through a versioned Shared SEO Evidence
contract/API/projection. The contract includes Project, source module,
evidence type/version, provider/endpoint, normalized parameters, request
fingerprint, market/language scope, fetched/expiry timestamps, provider task
or request identity, cost, provenance, artifact reference, and status.

Every recommendation generation pins:

```text
Project identity/version
SiteProfile version
ProjectOutreachProfile version
keyword/shared-evidence snapshot versions
market/location/language scope
qualification and visibility contracts
provider request fingerprints used by the generation
```

An upstream edit never changes an in-flight generation. It produces a new
input version for a new operation.

## 4. DataForSEO Boundary

One provider account and credential-health view may serve the integrated
product, but module operations remain isolated.

1. Current upstream keyword/competitor/SERP/content evidence may be reused
   when Project, endpoint, normalized parameters, market/language, provenance,
   and freshness match the generation.
2. Stale, untraceable, or parameter-mismatched evidence is rejected.
3. Backlinks owns candidate Traffic, Spam, and Authority qualification.
4. Candidate qualification uses a current authorized live artifact for the
   generation. The same persisted artifact is reused only for the same
   generation/request fingerprint.
5. Page refresh, navigation, polling, restart, and Workflow replay never
   create paid calls.
6. Missing credentials, invalid credentials, insufficient provider balance,
   rate limiting, timeout, outage, unknown charge, and explicit blocking are
   different product states with exact recovery actions.
7. Phase M1A does not centralize every existing DataForSEO client. A shared
   provider coordinator is a later optional architecture decision after the
   evidence contract and idempotency behavior are proven.

## 6. Coding Task Contract

Every future coding task starts with a task card containing:

```text
Task ID
selected phase
target repository, branch, and baseline commit
current git status
owned files
prohibited files and adjacent phases
database migration ownership, if any
provider/Gmail/AI call ceiling
required tests and runtime checks
result document path
exit criterion
stop conditions
```

Before editing, the task repeats the three-pass re-entry audit from the
implementation plan:

1. ownership and static conflict;
2. timeout, retry, cost, and idempotency;
3. compatibility, rollout, and activation.

The task stops when:

- another unfinished task owns an overlapping file;
- the current baseline no longer descends from the audited integrated commit
  and the new changes have not been reviewed;
- migration heads or deployment manifest do not describe one graph;
- frontend and backend contracts would be deployed in incompatible states;
- a paid request has an ambiguous dispatch outcome;
- the phase would require behavior owned by a later phase;
- the phase exit criterion cannot be proven.

Stopping for one of these reasons produces a truthful `BLOCKED` or
`INPUT_REQUIRED` result. It does not trigger an adjacent refactor.
