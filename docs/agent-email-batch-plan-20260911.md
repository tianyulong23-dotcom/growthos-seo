# Agent 调用现有邮件业务能力接入方案

日期：2026-09-11

## 目标与边界

项目已有业务代码负责生成草稿、审批、发送和邮件跟踪。Agent 的职责是理解用户意图、选择工具、传入正确参数、按真实结果组织后续调用，而不是重新实现这些业务。

本修订替代原方案中新建批次记录、专用批次界面、额外发送审批清单系统等预设。先检查现有接口和 Agent 工具的对应关系，只补缺失的调用适配、必要的调用说明和测试。

当前按用户授权分步实施；本轮接入只读邮件跟踪工具，不批准或发送邮件，不修改 Gmail 配置。此前“4～7 天”及“数小时到 1～2 天”的粗估均不作为本方案承诺；按实际缺口判断工作量。

## 已完成的草稿入口

实现邮件中心的“草稿”页签，展示当前项目外链机会绑定的待处理草稿，支持正文预览、刷新、分页和打开现有编辑页。Agent 和手动流程使用同一份已保存数据，不依赖 Gmail 连接状态。

此列表不是 Gmail 草稿箱，也不是历史版本归档。当前复用机会列表的游标接口，每次读取最多 100 个机会，再展示其中的草稿；“加载更多”继续查询后续机会。已进入邮件状态查看流程的机会不放入待处理草稿列表。

保留此入口，不为 Agent 接入重做邮件中心或编辑器。下方验证记录属于此前草稿入口交付，不代表后续工具接入已经完成。

## 第一步：盘点接口与工具

对照当前代码逐项填写下表，记录实际接口或服务入口、Agent 工具名称、参数、权限、返回状态及测试位置。不能把“页面已有功能”直接等同于“Agent 已能调用”，也不能把“未接工具”当作“缺少业务功能”。

| 用户需求 | 优先复用的业务能力 | 本次核对事项 |
| --- | --- | --- |
| 选择项目和目标 | 项目、机会、联系人、推广目标查询 | 项目归属、真实 ID、分页与联系人状态 |
| 生成草稿 | 创建草稿、查询任务、读取草稿 | 核验此前已接工具；根据任务结果取得正文和版本 |
| 发送前检查 | 现有发送就绪与预检接口 | 发件账号、联系人、草稿版本、阻塞原因 |
| 审批与发送 | 现有审批接口、发送任务接口 | 调用顺序、用户确认机制、幂等和权限要求 |
| 批量操作 | 现有批量接口；若无则复用单项接口 | 是否已有批量入口、调用数量限制及逐项结果 |
| 跟踪发送 | 现有发送队列、任务详情和状态查询 | 区分排队、失败、提供商接受及结果不确定 |
| 跟踪回信 | 现有邮件列表、会话、同步和回复匹配能力 | 已保存邮件与同步状态、项目及会话关联 |

盘点结果只分三类：已接通且可复用、已有接口但缺 Agent 适配、存在经代码验证的必要缺口。最后一类必须说明具体阻塞，不能据此擅自增加平台或管理系统。

## 第二步：最小化补齐调用

- 沿用当前 Agent 工具注册、项目权限委托和后端调用模式；已能正确调用的工具不重写。
- 给未接通的业务接口补薄适配层：参数校验、现有接口调用、返回必要结果。业务判断、状态变更和凭据管理继续由现有服务负责，不在工具层复制。
- 明确工具适用条件及先后关系；项目、机会、草稿、版本、发送任务和会话 ID 必须来自查询或执行结果，不能由模型编造。
- 原样遵守后端权限、审批、版本和发送约束；缺少授权时停止并说明原因，不让模型自行授权或扩大范围。
- 返回真实任务 ID、逐项状态及可操作的错误原因，避免把“请求已提交”写成“操作成功”。

### 单封操作顺序

生成：确定项目和目标 -> 调用创建草稿 -> 查询任务 -> 读取并核验草稿 -> 返回邮件中心对应入口。

发送：读取指定草稿及当前状态 -> 沿用现有预检和确认机制 -> 在已有有效授权下按接口要求审批、提交发送 -> 查询发送任务。

具体审批与预检先后以现有服务契约为准。如果现有审批必须由用户在页面完成，Agent 引导用户完成后继续，不通过工具冒充人工审批。

跟踪：读取发送任务 -> 按真实状态汇报 -> 查询关联邮件及回信。需要同步时调用已有受控同步能力；Gmail 不可用则明确数据尚未更新，不能把“未查到回信”说成“确定没有回信”。

### 批量操作方式

- 有现成批量接口就直接接入，不再实现一套。
- 只有单项接口时，针对用户指定的有限目标清单组织逐项调用，优先沿用 Agent 已有工具循环和执行限制；先串行跑通，不预设新的批量工具或并发调度器。
- 复用已有任务记录、幂等键与状态查询。超时或响应丢失先查执行结果，不重新生成标识后盲目重发。
- 汇总每项的成功、处理中、失败或阻塞原因。重试必须遵守现有接口规则，不重复执行已成功项。
- 授权必须覆盖实际发送目标；“帮我生成多封草稿”不等于“允许发送”。批量也不绕过单封现有的审批和版本检查。
- 如果单项接口和现有 Agent 执行记录不足以安全恢复重复请求，单独列出证据及最小修补建议，不默认新建批次数据库。

### 结果表述

草稿已生成不等于已审批；已审批不等于已发送；发送任务已创建不等于提供商已接受；提供商接受不等于最终送达或已读。按现有服务的状态契约报告结果，不额外发明成功状态。

## 第三步：验证调用是否正确

1. 工具适配测试：验证真实接口映射、参数传递、项目和组织隔离、权限拒绝及错误返回。
2. 单封链路：验证生成、查询任务、读取草稿；发送链路使用模拟返回验证现有预检、审批要求和任务提交顺序，不触发真实发送。
3. 批量调用：用有限清单验证部分失败、重复请求、超时后查状态、只继续未完成项；不扩展业务功能。
4. 跟踪查询：验证发送状态与对应邮件会话关联，区分同步不可用、数据未更新和已发现回复。
5. 本地对话验收：Agent 调用结果与邮件中心保存的数据对照。没有实际发送的部分明确标为模拟验证，不能标为真实发送通过。
6. 真实发送及后续回信验收：仅在另行取得具体发送授权且 Gmail 就绪后进行。

完成标准：用户通过对话能触发现有业务接口，参数、权限、调用顺序和结果解释正确；页面与 Agent 读取同一业务事实。不是要求新增一套邮件业务系统。

## 明确不做

- 不新建批次管理数据库、独立任务平台或发送队列。
- 不预设新增草稿列表 API、批次筛选界面、另一套审批清单系统。
- 不重做现有邮件中心、编辑器、审批、发送、同步或回信匹配逻辑。
- 不增加定时营销、后台持续监控、自动回复或长期免确认授权。
- 不修复 Gmail，不更改现有安全规则，不把方案批准当成真实发送授权。

如盘点发现必要能力确实缺失，先记录具体接口缺口和最小补充范围，再决定是否扩大实施范围。
